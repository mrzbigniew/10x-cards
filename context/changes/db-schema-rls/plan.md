# Database Schema + RLS Implementation Plan

## Overview

Create Supabase migration files for `decks`, `cards`, and `card_sr_state` tables with Row Level Security policies enforcing per-user data isolation, then generate TypeScript types from the resulting schema. This is the foundation slice — every other slice depends on it being in place.

## Current State Analysis

- `supabase/migrations/` exists but is **empty** — no schema files yet
- `supabase/config.toml` is fully configured (project ID `10x-cards`, PostgreSQL 17, local stack on ports 54321-54327)
- Supabase CLI `^2.101.0` is installed as a dev dependency
- `@supabase/supabase-js ^2.99.1` and `@supabase/ssr ^0.10.3` are installed
- Auth is fully wired: `src/lib/supabase.ts`, `src/middleware.ts`, and three API routes in `src/pages/api/auth/`
- No TypeScript database types file exists yet (`src/lib/database.types.ts` is absent)
- `ts-fsrs` is not yet installed

### Key Discoveries

- `src/lib/supabase.ts` reads `SUPABASE_URL` and `SUPABASE_KEY` from `astro:env/server` — environment schema is already declared in `astro.config.mjs`
- `src/middleware.ts` stores `user: User | null` in `context.locals` — downstream API routes already have auth context available
- `src/env.d.ts` declares `App.Locals.user: User | null` — this does not need to change for F-01

## Desired End State

Three tables (`decks`, `cards`, `card_sr_state`) are created in the local Supabase database via a single migration file. RLS is enabled on all three tables with identical four-policy shapes (SELECT/INSERT/UPDATE/DELETE restricted to the row owner via `auth.uid() = user_id`). A trigger auto-creates a `card_sr_state` row for every inserted card. TypeScript types are generated at `src/lib/database.types.ts` and `npm run typecheck` passes.

### Verification

- `supabase db reset` completes without errors
- All three tables are visible in Supabase Studio (http://localhost:54323)
- Attempting to SELECT another user's deck via direct SQL returns 0 rows (RLS blocks it)
- `src/lib/database.types.ts` exists and exports a `Database` type
- `npm run typecheck` exits 0

## What We're NOT Doing

- No application code changes (no API routes, no UI, no service layer) — that's S-01 through S-05
- No `supabase db push` to a remote project — local development only in this phase
- No Supabase Edge Functions
- No additional tables beyond the three defined here
- No review log / history table for SR ratings — current state only (review history is a v2 concern)
- No `generation_sessions` table — source text is transient per the privacy NFR (not persisted)

## Implementation Approach

Single migration file approach: one timestamped SQL file defines all tables, indexes, triggers, and RLS policies in dependency order. The `ts-fsrs` npm package is installed first to document the library version the schema was designed against. After applying the migration locally, TypeScript types are generated from the live local schema.

## Critical Implementation Details

- **Trigger security**: the `create_card_sr_state` trigger function must be declared `SECURITY DEFINER SET search_path = public` so it can write to `card_sr_state` even when RLS is enabled. Without `SECURITY DEFINER` the trigger runs as the invoking user, which is fine here (user_id is available as `NEW.user_id`) — but explicit `SECURITY DEFINER` + `SET search_path = public` is the Supabase-recommended pattern for trigger functions and prevents search-path injection.
- **SR state column `state`**: the `smallint` values 0–3 map directly to ts-fsrs `State` enum (`New=0`, `Learning=1`, `Review=2`, `Relearning=3`). Do not remap to strings — the application layer uses the integer values directly when calling ts-fsrs functions.
- **`due` initial value**: new `card_sr_state` rows get `due = now()` by default, meaning every new card is immediately available in today's review session. This is the correct FSRS starting state for a "New" card.

## Phase 1: Schema Migration

### Overview

Install `ts-fsrs`, generate the migration file with `supabase migration new`, fill it with the full schema SQL, then apply it locally with `supabase db reset`.

### Changes Required

#### 1. Install ts-fsrs

**File**: `package.json` (dependency added via npm)

**Intent**: Install the FSRS spaced-repetition library whose Card interface defines the SR-state column shape. Installing it now documents the version constraint and makes the library available for downstream slices.

**Contract**: `npm install ts-fsrs` adds `ts-fsrs` to `dependencies` in `package.json`.

#### 2. Create the migration file

**File**: `supabase/migrations/<timestamp>_initial_schema.sql` (filename generated by `supabase migration new initial_schema`)

**Intent**: Define all three tables, helper trigger function, auto-create trigger, indexes, and RLS policies in a single atomic file. This is the load-bearing schema that all other slices build on.

**Contract**: Run `npx supabase migration new initial_schema` to generate the timestamped file, then fill it with the SQL below. Column names here are the source of truth for all downstream slices — do not rename them.

```sql
-- ── Shared trigger function ──────────────────────────────────────────────
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$;

-- ── decks ────────────────────────────────────────────────────────────────
CREATE TABLE decks (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    uuid        NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  name       text        NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX decks_user_id_idx ON decks (user_id);

ALTER TABLE decks ENABLE ROW LEVEL SECURITY;
CREATE POLICY "decks: owner select" ON decks FOR SELECT USING (auth.uid() = user_id);
CREATE POLICY "decks: owner insert" ON decks FOR INSERT WITH CHECK (auth.uid() = user_id);
CREATE POLICY "decks: owner update" ON decks FOR UPDATE USING (auth.uid() = user_id);
CREATE POLICY "decks: owner delete" ON decks FOR DELETE USING (auth.uid() = user_id);

CREATE TRIGGER decks_updated_at
  BEFORE UPDATE ON decks
  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();

-- ── cards ────────────────────────────────────────────────────────────────
CREATE TABLE cards (
  id         uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  deck_id    uuid        NOT NULL REFERENCES decks(id) ON DELETE CASCADE,
  user_id    uuid        NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  front      text        NOT NULL,
  back       text        NOT NULL,
  source     text        NOT NULL CHECK (source IN ('ai', 'manual')),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX cards_deck_id_idx ON cards (deck_id);
CREATE INDEX cards_user_id_idx ON cards (user_id);

ALTER TABLE cards ENABLE ROW LEVEL SECURITY;
CREATE POLICY "cards: owner select" ON cards FOR SELECT USING (auth.uid() = user_id);
CREATE POLICY "cards: owner insert" ON cards FOR INSERT WITH CHECK (auth.uid() = user_id);
CREATE POLICY "cards: owner update" ON cards FOR UPDATE USING (auth.uid() = user_id);
CREATE POLICY "cards: owner delete" ON cards FOR DELETE USING (auth.uid() = user_id);

CREATE TRIGGER cards_updated_at
  BEFORE UPDATE ON cards
  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();

-- ── card_sr_state ────────────────────────────────────────────────────────
-- One row per card. Holds the current ts-fsrs Card state.
-- state values: 0=New 1=Learning 2=Review 3=Relearning
CREATE TABLE card_sr_state (
  id             uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  card_id        uuid        NOT NULL UNIQUE REFERENCES cards(id) ON DELETE CASCADE,
  user_id        uuid        NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  due            timestamptz NOT NULL DEFAULT now(),
  stability      float4      NOT NULL DEFAULT 0,
  difficulty     float4      NOT NULL DEFAULT 0,
  elapsed_days   int4        NOT NULL DEFAULT 0,
  scheduled_days int4        NOT NULL DEFAULT 0,
  reps           int4        NOT NULL DEFAULT 0,
  lapses         int4        NOT NULL DEFAULT 0,
  state          smallint    NOT NULL DEFAULT 0 CHECK (state IN (0, 1, 2, 3)),
  last_review    timestamptz,
  created_at     timestamptz NOT NULL DEFAULT now(),
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX card_sr_state_user_id_idx ON card_sr_state (user_id);
CREATE INDEX card_sr_state_due_idx     ON card_sr_state (due);

ALTER TABLE card_sr_state ENABLE ROW LEVEL SECURITY;
CREATE POLICY "card_sr_state: owner select" ON card_sr_state FOR SELECT USING (auth.uid() = user_id);
CREATE POLICY "card_sr_state: owner insert" ON card_sr_state FOR INSERT WITH CHECK (auth.uid() = user_id);
CREATE POLICY "card_sr_state: owner update" ON card_sr_state FOR UPDATE USING (auth.uid() = user_id);
CREATE POLICY "card_sr_state: owner delete" ON card_sr_state FOR DELETE USING (auth.uid() = user_id);

CREATE TRIGGER card_sr_state_updated_at
  BEFORE UPDATE ON card_sr_state
  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();

-- Auto-create an SR state row for every new card
CREATE OR REPLACE FUNCTION create_card_sr_state()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
  INSERT INTO card_sr_state (card_id, user_id)
  VALUES (NEW.id, NEW.user_id);
  RETURN NEW;
END;
$$;

CREATE TRIGGER after_card_insert
  AFTER INSERT ON cards
  FOR EACH ROW EXECUTE FUNCTION create_card_sr_state();
```

## Phase 2: TypeScript Type Generation

### Overview

Start the local Supabase stack (if not already running), generate TypeScript types from the applied schema, save them to `src/lib/database.types.ts`, add a convenience npm script, and verify the project typechecks cleanly.

### Changes Required

#### 1. Add gen-types npm script

**File**: `package.json`

**Intent**: Expose type regeneration as a named script so any implementer can refresh types after future schema changes without having to remember the CLI invocation.

**Contract**: Add `"gen-types": "supabase gen types typescript --local > src/lib/database.types.ts"` to the `scripts` section.

#### 2. Generate and commit database types

**Prerequisite**: the local Supabase stack must be running (`npx supabase start`). If you restarted your machine after Phase 1, run `npx supabase start` before proceeding; the stack does not persist across reboots.

**File**: `src/lib/database.types.ts` (new file, generated — do not hand-write)

**Intent**: Produce the typed `Database` interface that downstream slices use when constructing typed Supabase clients and writing service functions. Generated output is committed to source control so CI can typecheck without running the local Supabase stack.

**Contract**: Run `npm run gen-types` while `npx supabase start` is active. The output file must export a top-level `Database` type. Commit the file as-is; do not edit it manually.

### Success Criteria

#### Automated Verification

- `src/lib/database.types.ts` exists and is non-empty after running `npm run gen-types`
- `npm run lint` exits 0 (typescript-eslint catches type errors introduced by the new types file)

#### Manual Verification

- Open `src/lib/database.types.ts` and confirm it contains `Tables` entries for `decks`, `cards`, and `card_sr_state` with the expected column names matching the migration

**After manual verification passes, this change is ready for commit and the roadmap F-01 item can be marked done.**

## Migration Notes

This is the first migration in an empty migrations directory. No rollback strategy is needed for initial development — `supabase db reset` re-applies from scratch. If the schema needs adjustment before any data exists, edit the migration file directly and run `supabase db reset` again rather than creating a new migration.
